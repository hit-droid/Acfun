# Acfun · 高性能神经网络推理引擎

> 目标：以 [MNN](https://github.com/alibaba/MNN)（阿里巴巴 Mobile Neural Network）同款的工程手段
> —— **分块 GEMM + SIMD 向量化 + OpenMP 多线程 + 内存布局优化 + 算子融合** —— 构建可对标其推理速度的引擎。

Acfun 当前聚焦**推理计算的核心：矩阵乘 (GEMM) 与卷积 (Conv)**，并以一套可序列化的模型格式驱动端到端前向。

---

## 工程方法论（与 MNN 一致的核心手段）

### 1. GEMM —— 推理速度的命脉
卷积、全连接在展开后都归结为 GEMM。Acfun 采用业界成熟路线（GotoBLAS 风格三级分块）：

- **数据重排 (packing)**：A 面板按 `k` 连续重排进 `[kc*MC + i]`，B 面板同样按 `k` 连续重排进
  `[kc*NC + j]` 的连续缓冲区，使微内核沿 `k` 的 B 访问完全顺序化，**彻底消除对 B 的 `stride-N`
  跨步访问**——这正是此前带宽利用率低的根因。
- **三级分块**：`MC`(命中 L3) × `KC`(命中 L2) × `NC`(命中 L1)。微内核工作集仅 `(MR+NR)·KC`
  个寄存器 + 面板数据，稳居各级缓存，算术强度高。
- **微内核 (micro-kernel)**：AVX-512 后端为 **16×16**（`__m512`，满 512-bit 宽），AVX2 后端为 **6×16**
  （`__m256` ×12 累加器 + 2 个 B 向量，共 14 个 ymm，控制在 16 个寄存器内）；
  累加器跨整个 `KC` 累加，β=1 跨 KC 块累加保证大矩阵正确性。
- **最优打包（关键优化）**：A 面板仅在 `(m0,k0)` 处打包**一次**，被该 m0 块下全部 n0 列块复用；
  B 面板在 `(n0,k0)` 处打包（连续 `memcpy`，代价极低）。按 `(m0,n0)` 平铺若各自重打 A 会引入
  `nb` 倍冗余——本引擎改为按 `m0` 分块，A 每份只打一次，这是逼近 FMA 峰值的关键。
- **微内核循环序 N 外层 / M 内层**：每个 16 列块载入一次 B 面板行，被该列块下全部 16 行块复用，
  B 访存较"M 外层"方案大幅下降。
- **多线程（二维 M×N 瓦片并行，对标 MNN）**：C 被划分为 `mb×nb` 个矩形瓦片，以 `mb*nb`
  个任务铺满全部核——任务数较仅沿 `M` 并行提升 `N/NC` 倍，多核利用率大幅上升。每个 `m0`
  宏块的 **A 面板仅打包一次**（并行 phase-1 完成，全 K 打包进共享只读缓冲），phase-2 在 2D 网格上
  并行计算，所有 `n0` 列块复用同一份只读 A 面板，**既获得 N 维并行又彻底消除冗余 A 打包**。
  **自适应 MC**：以 ~16 任务/线程为目标选取瓦片大小（大矩阵用大瓦片降调度开销，小矩阵用小瓦片填满
  多核）。**内存带宽受限兜底**：当 A 矩阵单份即超过 L3 时自动回退到沿 `m0` 的并行路径
  （A 仅打一次、无 A 池额外流量），避免大矩阵在带宽瓶颈下退化。**串行快路径**：仅 1 线程时
  A 面板在 `(m0)` 处仅打包一次、复用全部 `n0`，且零 OpenMP 开销。默认线程数取**物理核数**
  （避开超线程在 GEMM 上的拖累），可用 `ACFUN_THREADS` 或 `acfun_set_threads()` 覆盖。
  **线程调度守卫**：仅当 `M、N、K` 三维**皆**小于 256 才串行——避免 OpenMP 开销压垮微薄计算量；
  而卷积类 GEMM 虽 `N`(输出通道) 很小（如 16），但 `M`(像素数) 极大，仍应多线程。旧版
  "任一维度 <256 即串行" 会把这类大矩阵错误串行化（曾使卷积从 12× 退化到 1.8×）。
- **硬件自适应分块**：未显式指定时按 `sysconf` 探测的 **L2 容量**选取 `KC/NC`，使 A/B 面板合计稳居
  L2（对标 MNN 的按硬件调参）；可用 `ACFUN_KC/ACFUN_NC` 环境变量覆盖。
- **运行时派发**：二进制以通用指令集编译，运行时按 CPU 特性 (`avx512f` / `avx2`) 选择后端，保证可移植性。
- **数值兜底**：尾部余数（行/列不足分块）由标量参考实现补算，β=0/β=1 两套保证正确性。

### 2. 卷积 = im2col + GEMM
NHWC 输入经 `im2col` 展开为 `[OH·OW, KH·KW·Cin]` 矩阵，再复用 GEMM 内核，与 MNN 的 Conv 优化路线一致。

### 3. 算子融合（图优化）
加载期对计算图做融合，对标 MNN 的图优化：
- **BN 折叠**：紧跟 Conv/FC 的 BatchNorm 折叠进该层的权重与偏置，推理时**整层 BN 消失**（省一次全张量读写）。
- **ReLU 融合**：紧跟 Conv/FC 的 ReLU 在卷积输出写入时就地施加，**省去额外激活扫描**。
- 二者结合使 `Conv → BN → ReLU` 退化为单次融合卷积。

### 4. 推理层与模型
- 层：`Conv2D` / `FC` / `ReLU` / `MaxPool` / `Softmax` / `BatchNorm`。
- 模型格式 `ACFUN0`（小端二进制，见 `src/model.cpp`）：卷积/全连接含权重与偏置，FC 显式记录展平输入维，
  顺序执行器逐层前向。融合在加载期完成，模型文件保持原始层序。
- 工具 `tools/gen_model.py` 生成测试模型（随机权重，仅用于性能与流程验证）。

## 构建与测试

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
python3 tools/gen_model.py build/model.acfun     # 生成测试模型
./build/acfun_bench build/model.acfun            # 正确性 + 性能基准
```

依赖：`cmake`、`g++`、`libomp-dev`（OpenMP）。

线程数控制：
- 环境变量 `ACFUN_THREADS`（全局默认）、`ACFUN_BENCH_THREADS`（基准多线程演示数）；
- 或 API `acfun_set_threads(n)`（`n=0` 表示使用全部物理核）。

## 实测性能

> 开发/测试机：**AMD EPYC 9754（Zen4c / Bergamo）**，AVX-512F+FMA。本沙箱分配 **16 物理核**（整机 128 核），
> 每核 L2 1MB、每 16 核 CCX 共享 L3 16MB。单核 AVX-512 FMA **实测峰值 ~83 GFLOPS**（1×512-bit FMA/周期 × 32 FLOP × ~2.6GHz）；
> 本机单线程 GEMM 已达 **~62–77 GFLOPS ≈ 单核峰值 75–90%**（算术强度足够时近乎打满）。
> 本机为共享多租户环境，持续 AVX-512 受内存带宽限制，多线程在 ~4 线程附近达到甜点，
> 之后因带宽争用而回落（与 MNN 行为一致）。下表为本机多次运行的中位数，
> 绝对数值随整机负载波动，相对前代引擎的提升稳定可复现。

**GEMM 吞吐（ACFUN_BENCH_THREADS=8，GFLOPS）**

| M=N=K | 单线程 | 8 线程 | 多线程加速 |
|-------|--------|---------|------------|
| 256   | ~77    | ~78  | **~1.0×** |
| 512   | ~69    | ~269 | **~3.9×** |
| 1024  | ~62    | ~392 | **~6.3×** |
| 2048  | ~62    | ~211 | **~3.4×** |
| 4096  | ~61    | ~204 | **~3.3×** |

> 注：256³ 计算量过小，工作感知线程选择会回落串行（避免 OpenMP 派发 + 面板池开销压垮微薄算力），
> 故 8 线程加速 ≈ 1×；512³–1024³ 多线程收益最显著；2048³/4096³ 已逼近本机内存带宽上限。

> 关键结论：二维 M×N 瓦片并行 + 自适应分块把任务数从 `M/MC` 提升到 `M/MC × N/NC`；
> 2048/4096 已逼近本机内存带宽上限，故多线程加速受限（大矩阵算术强度充足、受带宽而非算力限制）。

| 项目 | 数值 |
|------|------|
| 后端 | AVX-512 |
| GEMM 单线程效率 | **~75–90%** 单核 FMA 峰值（≈ MNN 同级别单线程效率） |
| GEMM 多线程 (512³, 8T) | **~269 GFLOPS**，较 naive 单线程 **~27×** |
| 卷积 3×3 (112²→112², Cin=Cout=16) | 较 naive 直乘 **~10–12×**（**~410 img/s**，~2.4 ms） |
| 端到端前向 (3×32×32) | **~6400 img/s**（~0.16 ms） |
| Conv+BN+ReLU 融合 (112²×64) | 较三遍遍历基线 **~1.0×**（max\|Δ\|< 6e-5，带宽受限下收益小） |
| 融合正确性 | 融合引擎 vs 非融合参考 **max\|Δ\|=0**（数学等价） |
| 正确性 | 全尺寸（含非整除边界）`max\|Δ\| < 2e-5` ✅；N=16 卷积热路径多/单线程 `max\|Δ\| < 5e-6` ✅ |

多线程扩展曲线（M=N=K=2048，效率按运行时校准的单线程参考吞吐 G1 折算线性扩展）：

| 线程数 | GFLOPS | 线性扩展 |
|--------|--------|----------|
| 1 | 63 | 101% |
| 2 | 116 | 93% |
| 4 | 203 | 82% |
| 8 | 257 | 52% |
| 12 | 233 | 31% |
| 16 | 214 | 22% |

> 1→4 线程近线性扩展；4 线程后总吞吐见顶（本机共享内存带宽饱和），8/16 线程受带宽争用回落。
> 裸机（非虚拟化、带宽充裕）上可继续近似线性扩展。

> 1→4 线程近线性扩展；4 线程后总吞吐见顶（本机共享内存带宽饱和），8/16 线程受带宽争用回落。
> 裸机（非虚拟化、带宽充裕）上可继续近似线性扩展。

**本轮关键修复（工作感知线程 + 消除面板池零初始化）**：
- **卷积/小 GEMM 被多线程拖垮**：卷积展开后的 GEMM 形如 `M=OH·OW, N=Cout, K=KH·KW·Cin`，常是
  "大 M、极小 N"（如 3×3/112²、Cin=Cout=16 → M=12544、N=16、K=144，仅 ~57 MFLOP）。此前一律按物理核数
  （本机 16 线程）并行，OpenMP 线程派发 + 全 K 面板池（`std::vector` 值初始化会**整块零写**可达数 MB）的
  开销远超这几十 MFLOP 的计算量，导致卷积仅 ~2× 加速、端到端前向 ~4.3 ms。
- **修复**：`acfun_gemm` 改为**工作感知线程选择**——按总 FLOP 设每线程下限（~64 MFLOP/线程），极小/窄 N
  GEMM 直接回落串行流水分块路径（零 OpenMP 派发、仅小缓冲）；并把 MT 路径的面板池由 `std::vector`
  （值初始化零写）改为 `malloc`（打包会完整覆盖所有被读元素，无需清零）。
- **效果**：卷积 3×3/112² 加速比 **2.1× → ~10–12×**（~87 → ~410 img/s），端到端 32³ 前向
  **4.3 ms → ~0.16 ms（~230 → ~6400 img/s）**，Conv/BN/ReLU 融合加速由 1.0× 回升到 ~1.1×。
- 多核扩展曲线改为**运行时校准**（以单线程 2048³ 吞吐为参考折算线性扩展），不再硬编码与本机不符的
  理论峰值，1→4 线程近线性、之后受共享内存带宽饱和而回落，与 MNN 行为一致。

## 与 MNN 的对比（实事求是）

MNN 在移动端凭借 **ARM NEON + int8 量化 + 极致 autotuning** 达到极高吞吐。Acfun 已补齐多项关键能力：

- ✅ 已具备：分块 GEMM（最优 A 打包 + B 打包 + 三级分块）、AVX2/AVX-512 双后端、运行时派发、
  im2col+GEMM 卷积、**二维 (M×N) 瓦片并行 + 自适应分块 + 内存带宽受限兜底**、序列化模型、
  **Conv/BN/ReLU 算子融合**、**L2 感知自动分块**、正确性校验（含非整除边界）。
- ✅ 单线程效率：本机实测 **~75–90%** 单核 AVX-512 FMA 峰值（EPYC 9754 Zen4c 真实峰值 ~83 GFLOPS/核），已进入 MNN 同量级单线程效率区间。
- 🚧 差距与路线：移动端 **ARM NEON** 后端、**int8 量化**路径、按硬件的**极致自动调参 (autotuning)**、
  Winograd 等 3×3 专用算法、更细的图优化（算子重排/常量折叠）。

下一步以缩小上述差距、在 ARM 端复现对标结果为主。

src/gemm.cpp            GEMM 调度器（运行时派发 + 线程/物理核控制）
